## 1. Dataset Overview

The russellmitchell testbed simulates a small enterprise network ("Smith" at russellmitchell.com) with 22 hosts over a 4-day period (Jan 21-25, 2022). A multi-stage cyberattack occurs on Jan 24. The dataset contains raw logs from all hosts and ground truth labels for attack-related events.

The dataset is generated by the AIT Kyoushi simulation framework, which defines 3 distinct attack scenarios in `environment/datasets/`. The raw log data in `gather/` is shared across all scenarios (same network, same employees, same background traffic), but the attack scope, labeling rules, and processed outputs differ per scenario. We selected the full "scenario" configuration.

### Scenario Comparison

| Aspect | scenario (full) - ours | scenario1 (no exfil) | scenario2 (exfil only) |
|--------|------------------------|---------------------|----------------------|
| Foothold attack | Yes | Yes | No |
| Escalation | Yes | Yes | No |
| DNS exfiltration | Yes | No | Yes |
| Labeling rules | All 6 | 5 (no dnsmasq) | 2 (audit + dnsmasq only) |
| Labeled lines | 61,862 | ~7,827 | ~54,046 |
| Log sources with labels | 8 | 7 | 3 |
| CPU monitoring | Yes | Yes | No |

Why the full scenario: it gives us the most labeled data, the most complex attack chain, and the most log types to design tables around. Under scenario1, we would lose all 54K DNS exfiltration labels. Under scenario2, we would lose the entire web attack/escalation narrative and have only 3 log sources.

## 3. Ground Truth Labels

5 of 22 hosts have label files. 8 specific log files have attack annotations. We focus our analysis where labels exist.

### Label Format (JSONL)

Each line maps a raw log line number to attack labels:

```json
{"line": 1860, "labels": ["attacker_change_user", "escalate"], "rules": {"attacker_change_user": ["attacker.escalate.audit.su.login"], "escalate": ["attacker.escalate.audit.su.login"]}}
```

- `line`: line number in corresponding raw log file
- `labels`: attack phase tags (can be multi-valued, events frequently have 2-3 co-occurring labels)
- `rules`: labeling rule that triggered the tag

Unlabeled log lines = normal (non-attack) behavior.

### Labeling Rules (6 files)

| Rule File | Covers | Scenarios Active In |
|-----------|--------|-------------------|
| `0_auth.yaml` | auth.log patterns (su, sudo, session) | scenario, scenario1 |
| `apache.yaml` | HTTP access/error (dirb, wpscan, webshell) | scenario, scenario1 |
| `audit.yaml` | Kernel audit (su login, escalation) | scenario, scenario1, scenario2 |
| `dnsmasq.yaml` | DNS exfiltration (dnsteal domain matching) | scenario, scenario2 |
| `monitoring.yaml` | CPU spikes during password cracking | scenario, scenario1 |
| `openvpn.yaml` | VPN connections from attacker IP | scenario, scenario1 |

## 6. Selected Data Scope

### Why These Files

We selected all 8 labeled log files from the full "scenario" configuration:

1. They have ground truth - we can validate queries against known attack events
2. They cover the full attack chain - from initial VPN access through exfiltration
3. They span 5 hosts - enables cross-host correlation
4. They total 295,243 rows - nearly 6x the minimum requirement
5. They require normalization - 7 different log formats (text, syslog, key-value, JSON)
6. They are the richest scenario - using a reduced scenario would lose labeled data

### Log-by-Log Selection Rationale

| # | Log | Rows | Why Selected |
|---|-----|-----:|-------------|
| 1 | DNS (dnsmasq.log) - inet-firewall | 275,900 | Largest log. Contains DNS exfiltration where DNSteal encodes stolen data in subdomain queries. Normal DNS traffic provides baseline for anomaly detection. |
| 2 | Apache access.log - intranet_server | 8,530 | Contains the web attack chain: service scan, dirb, WPScan, webshell upload, command execution. Rich HTTP fields (method, path, status, user-agent). |
| 3 | Apache error.log - intranet_server | 36 | Every line is attack-related (directory traversal attempts, script probing). Correlates with access log. |
| 4 | VPN (openvpn.log) - vpn | 5,537 | Entry point of attack. Shows attacker VPN connection among legitimate remote employee connections. |
| 5 | Audit log - intranet_server | 2,316 | Kernel-level syscall data. Captures privilege escalation (su to user, credential access). |
| 6 | Auth log - intranet_server | 272 | Authentication events (session opens/closes, su attempts). |
| 7 | CPU monitoring - monitoring | 1,920 | Time-series metric (45-sec intervals). CPU spikes during the password cracking window. |
| 8 | Audit log - internal_share | 732 | Captures exfiltration service start on file server. Establishes lateral movement. |

### Expected Cross-Log Correlation

The attacker should be traceable across multiple log sources using IP addresses:
- External IP (192.168.230.122) in VPN logs
- VPN-assigned internal IP (172.19.131.174) in Apache, DNS, and audit logs

This cross-host correlation is one of the key analytical capabilities we plan to demonstrate.

## 7. Planned Schema (PostgreSQL)

### Tables (8 tables, exceeds minimum of 4)

```
hosts                   <- dimension: 22 hosts with metadata (from servers.yaml)
log_events              <- fact: all parsed log events
attack_labels           <- label records linked to log_events
http_events             <- parsed fields from Apache access/error logs
dns_events              <- parsed fields from dnsmasq logs
auth_events             <- parsed fields from auth.log + audit.log
vpn_events              <- parsed fields from openvpn.log
system_metrics          <- parsed fields from cpu.log
```

### Relationships

```
hosts (1) ------< (N) log_events
log_events (1) --< (N) attack_labels
log_events (1) ---- (1) http_events      (for log_type = 'http')
log_events (1) ---- (1) dns_events       (for log_type = 'dns')
log_events (1) ---- (1) auth_events      (for log_type = 'auth')
log_events (1) ---- (1) vpn_events       (for log_type = 'vpn')
log_events (1) ---- (1) system_metrics   (for log_type = 'metrics')
```

### Why This Design Requires Normalization

Raw state: each log type is a flat text file with completely different schemas. Loading them as-is would be one giant denormalized table with NULLs everywhere (a DNS event has no HTTP status code; an HTTP event has no DNS query domain).

Normalization steps:
- 1NF: parse multi-value fields (labels array to separate rows in attack_labels)
- 2NF: separate host metadata from event data (host info repeated on every log line)
- 3NF: remove transitive dependencies (log_type-specific fields into sub-tables; attack_phase derived from label_name into a lookup)

### Attribute Inventory (46 unique across tables)

| Table | Key Attributes |
|-------|----------------|
| hosts | host_id, hostname, ip_address, host_type, network_zone, os_distribution |
| log_events | event_id, host_id (FK), timestamp, log_type, source_file, line_number |
| attack_labels | label_id, event_id (FK), label_name, attack_phase, rule_name |
| http_events | event_id (FK), client_ip, method, path, query_string, protocol, status_code, bytes_sent, user_agent, referer |
| dns_events | event_id (FK), action, query_type, domain, client_ip, extra_ip, is_exfiltration |
| auth_events | event_id (FK), event_type, username, service, pid, uid, acct, exe, op, result, terminal |
| vpn_events | event_id (FK), user, client_ip, client_port, message, event_type |
| system_metrics | event_id (FK), hostname, cpu_total_pct, cpu_user_pct, cpu_system_pct, cpu_idle_pct, cpu_iowait_pct, cores |

### SQL Type Mapping

| Column | SQL Type | Source |
|--------|----------|--------|
| timestamp | TIMESTAMP WITH TIME ZONE | All logs |
| client_ip, extra_ip | VARCHAR(45) | DNS, Apache, VPN |
| domain | VARCHAR(309) | DNS (long due to exfil-encoded subdomains) |
| status_code | INTEGER | Apache access |
| bytes_sent | INTEGER | Apache access |
| path, user_agent, message | TEXT | Apache, VPN, Auth |
| method, protocol, action, event_type | VARCHAR(20) | Various |
| cpu_*_pct | DECIMAL(10,4) | CPU monitoring |
| is_exfiltration | BOOLEAN | DNS |

## 8. Analytical Questions (for SQL queries)

These tie directly to the project problem ("Can we detect and reconstruct a cyber attack from distributed logs?"):

Basic:
1. How many events per host per day? (GROUP BY, COUNT)
2. What HTTP status codes appear during the attack window vs. normal? (WHERE, GROUP BY)
3. Which users authenticated during the attack? (JOIN hosts + auth_events)
4. Top 10 most queried DNS domains? (ORDER BY, LIMIT)
5. Event count by log type? (GROUP BY)
6. VPN connections by hour of day? (date functions, GROUP BY)
7. HTTP requests by method and path prefix? (GROUP BY, LIKE)
8. Attack labels by phase? (GROUP BY on attack_labels)

Advanced:
1. Reconstruct attack timeline ordered by timestamp across all 8 log types (CTE + UNION + ORDER BY)
2. Running count of events per host leading up to the attack (window function: COUNT OVER)
3. DNS query frequency per minute - detect the exfiltration spike (window function + time bucketing)
4. Simulate scenario1 vs scenario2 - filter labels by rule source to show what would be visible under each scenario (subquery + conditional aggregation)
5. CPU anomaly detection - find the password-cracking window where cpu_total_pct jumps from baseline to 100% (self-join or LAG window function)
6. Cross-host attacker trace - join log_events + hosts on IP to track attacker across log sources (multi-table JOIN with IP matching)
7. Create a view for the attack dashboard (CREATE VIEW combining log_events + attack_labels + hosts)
8. Index performance comparison on timestamp queries (CREATE INDEX + EXPLAIN ANALYZE)

## 9. Key Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| DNS log is 93.4% of total rows - skews analysis | Unbalanced tables | Analyze DNS separately; use sampling for dashboards; partition by is_exfiltration flag |
| Some tables are small (auth: 272, error: 36) | May look like toy data | These are real logs from a simulation; small count matches real enterprise auth volume over 4 days |
| Timestamp formats differ across 7 log types | Parsing complexity | Normalize all timestamps to UTC datetime; map to TIMESTAMP WITH TIME ZONE during ingestion |
| Labels reference line numbers, not timestamps | Must preserve line numbers during parsing | Add `line_number` column to every parsed table; join labels on (source_file, line_number) |
| Audit log has nested key-value pairs | Complex parsing | Need a key-value parser that handles nested `msg='...'` blocks; extract only fields needed for schema |
| Attacker uses 2 different IPs | Cross-log correlation requires matching both IPs | Both IPs (192.168.230.122 external, 172.19.131.174 VPN-internal) from `attacker.yaml`; JOIN conditions must match on either |
| Scenario confusion | Labels are scenario-dependent | Document that `labels/` corresponds to full scenario; note which rules are active per scenario |
