\section{SQL Analysis and Results}
\label{sec:sql}

\subsection{Methodology}
The query portfolio contains \textbf{23 SQL query items}: 7 basic and
16 advanced, committed across \textbf{6 basic and 13 advanced}
\texttt{.sql} files in the project repository under
\texttt{sql/queries/basic/} and \texttt{sql/queries/advanced/}. (Two
files each hold more than one query: \texttt{naman\_basic\_queries.sql}
holds two basic queries B6 and B7, and \texttt{naman\_advanced\_queries.sql}
holds four advanced queries A4 through A7.) The portfolio is augmented
by one saved view (\texttt{v\_privilege\_escalation\_timeline}) and
one composite index (\texttt{idx\_audit\_event\_host\_timestamp}),
both managed by Alembic migration \texttt{742e860d116f}. Together they
cover all six SQL categories called out by the rubric: subqueries,
common table expressions, window functions, multi-table joins of three
or more tables, performance indexing with \texttt{EXPLAIN ANALYZE},
and saved views.

Every query is reproducible. A reader who has followed the load steps
in Section~\ref{sec:dbsetup} can paste any \texttt{SELECT} below into
their psql session and obtain the same numeric result. For queries
where the underlying file in the repository contains more text (header
comments documenting story role, expected result, or recommendation),
the report includes the executable \texttt{SELECT} body and refers the
reader to the file path for the full annotation.

For the longer deep-dive queries (A4, A5, A6, A7, the EXPLAIN
demonstration, and the saved view) we include the question, the SQL
listing, a numeric result summary, and an interpretation paragraph.
For the simpler queries we keep the same four elements but compress
the SQL into a smaller listing block.

\subsubsection{B1 (River): Labeled lines per source host}
\textbf{Question.} Which hosts contribute the most labeled attack
evidence across the corpus?

\begin{lstlisting}[language=SQL]
SELECT source_host,
       COUNT(*) AS labeled_line_count
FROM labeled_line
GROUP BY source_host
ORDER BY labeled_line_count DESC;
\end{lstlisting}

\textbf{Result.} Five rows, one per host that carries at least one
labeled line. \texttt{internal\_share} dominates by raw count because
of the DNS-tunneling exfiltration; \texttt{intranet\_server} contributes
the bulk of the foothold lines from \texttt{access.log.2}; and
\texttt{inet-firewall} plus \texttt{monitoring} contribute the low-volume
side-channel labels.

\textbf{Insight.} The dominant host frames the rest of the analysis.
Once the team saw that \texttt{intranet\_server} is the only host with
labels distributed across multiple phases (\texttt{initial\_access},
\texttt{privilege\_escalation}, plus side-channel
\texttt{exfiltration}-adjacent labels), it became the natural focal
host for the deep-dive queries.

\subsubsection{B2 (River): Attack labels per phase}
\textbf{Question.} How rich is the label taxonomy in each attack phase?
\begin{lstlisting}[language=SQL]
SELECT ap.phase_name,
       COUNT(al.label_id) AS label_count
FROM attack_phase ap
FULL OUTER JOIN attack_label al
  ON al.phase_id = ap.phase_id
GROUP BY ap.phase_id, ap.phase_name
ORDER BY label_count DESC;
\end{lstlisting}

\textbf{Result.} Seven rows (one per phase) showing label counts in the
range one to seven. \texttt{exfiltration} and
\texttt{privilege\_escalation} carry the most distinct labels;
\texttt{persistence} and \texttt{lateral\_movement} are sparsest.

\textbf{Insight.} Phases with richer taxonomies tend to be the phases
the dataset authors instrumented most carefully. The label-count
distribution shows where the dataset's designers expected detection
sophistication to land.

\subsubsection{B3 (River): Audit-event count per host}
\textbf{Question.} Which hosts produce \texttt{auditd} traces at all,
and how many events does each one emit?

\begin{lstlisting}[language=SQL]
SELECT h.hostname,
       h.host_key,
       COUNT(ae.event_id) AS event_count
FROM host h
INNER JOIN audit_event ae
  ON ae.host_id = h.host_id
GROUP BY h.host_id, h.hostname, h.host_key
ORDER BY event_count DESC;
\end{lstlisting}

\textbf{Result.} Two rows: \texttt{intranet\_server} (2{,}316 events)
and \texttt{internal\_share} (732 events).

\textbf{Insight.} Only two of the 22 testbed machines emit
\texttt{auditd}, which is consistent with the testbed configuration in
\texttt{servers.yaml}. This is the sole reason the audit domain has
3{,}048 rows in total: there is no missing data, the corpus simply
constrains audit instrumentation to two hosts.

\subsubsection{B4 (Ishaan): Labeled lines per attack phase}
\textbf{Question.} How heavily is each phase represented in the labeled
data, by line count?
\begin{lstlisting}[language=SQL]
SELECT ap.phase_name, COUNT(*) AS labeled_lines
FROM attack_phase ap
JOIN attack_label al        ON al.phase_id  = ap.phase_id
JOIN labeled_line_label lll ON lll.label_id = al.label_id
GROUP BY ap.phase_name
ORDER BY labeled_lines DESC;
\end{lstlisting}

\textbf{Result.} Seven rows. \texttt{exfiltration} dominates with
roughly 53{,}000 lines (driven by per-DNS-query labels on
\texttt{internal\_share/dns.log}); \texttt{initial\_access} carries
the second-largest count (driven by foothold labels on
\texttt{intranet\_server/access.log.2});
\texttt{privilege\_escalation} carries only 82 lines.

\textbf{Insight.} Volume is a misleading detection metric on this
dataset: the lowest-count phase (privilege escalation) is the most
operationally significant. Section~\ref{sec:conclusion} returns to
this point.

\subsubsection{B5 (Ishaan): Top-10 detection rules}
\textbf{Question.} Which detection rules contribute the most label
firings?
\begin{lstlisting}[language=SQL]
SELECT rule_name, COUNT(*) AS times_used
FROM labeled_line_rule
GROUP BY rule_name
ORDER BY times_used DESC
LIMIT 10;
\end{lstlisting}

\textbf{Result.} Ten rows. \texttt{dnsteal.domain.match} is rank one
with roughly 53{,}000 firings, exfiltration-adjacent rules round out
the top half, and audit-derived rules appear in the bottom half with
low absolute counts but high per-firing severity.

\textbf{Insight.} The top-10 view by raw firings buries the
audit-domain rules. Query A14 (Section~\ref{sec:adv-naman-priv-esc})
re-ranks the same data after restricting to the
\texttt{privilege\_escalation} phase, which surfaces those audit rules
to the top.

\subsubsection{B6 (Naman, Q1 of \texttt{naman\_basic\_queries.sql}): Service activity baseline}
\textbf{Question.} What is the baseline service activity on the two
audit-instrumented hosts? Establishing the baseline lets later queries
see which one stop/start pair stands out as anomalous.

\begin{lstlisting}[language=SQL]
SELECT h.host_key,
       am.unit AS service_name,
       SUM(CASE WHEN ae.type = 'SERVICE_START'
                THEN 1 ELSE 0 END) AS starts,
       SUM(CASE WHEN ae.type = 'SERVICE_STOP'
                THEN 1 ELSE 0 END) AS stops
FROM audit_event ae
JOIN audit_service_event ase ON ase.event_id = ae.event_id
JOIN audit_message am        ON am.event_id  = ae.event_id
JOIN host h                  ON h.host_id    = ae.host_id
GROUP BY h.host_key, am.unit
ORDER BY h.host_key,
         SUM(CASE WHEN ae.type = 'SERVICE_START' THEN 1 ELSE 0 END)
       + SUM(CASE WHEN ae.type = 'SERVICE_STOP'  THEN 1 ELSE 0 END) DESC;
\end{lstlisting}

\textbf{Result.} 33 (host, service) rows.
\texttt{phpsessionclean} dominates \texttt{intranet\_server} with 384
events. The \texttt{put} service on \texttt{internal\_share} has a
single start and a single stop amid hundreds of routine cron-driven
service events.

\textbf{Insight.} The \texttt{put} service start/stop pair is the
exfiltration service whose existence is later confirmed by attack
labels. The query is basic in its SQL, but it is the rare basic query
that produces an actionable detection signal on its own.

\subsubsection{B7 (Naman, Q2 of \texttt{naman\_basic\_queries.sql}): Phase coverage by log-source spread}
\textbf{Question.} Which attack phase generates evidence in the most
distinct log sources, and what is the line count behind that spread?
\begin{lstlisting}[language=SQL]
SELECT ap.phase_name,
       COUNT(DISTINCT lll.labeled_line_id) AS labeled_lines,
       COUNT(DISTINCT ll.source_host || '/' || ll.source_log)
         AS log_sources_affected
FROM attack_phase ap
JOIN attack_label al        ON al.phase_id  = ap.phase_id
JOIN labeled_line_label lll ON lll.label_id = al.label_id
JOIN labeled_line ll
  ON ll.labeled_line_id = lll.labeled_line_id
GROUP BY ap.phase_name
ORDER BY labeled_lines DESC;
\end{lstlisting}

\textbf{Result.} Seven rows. \texttt{exfiltration} dominates by line
count (53K) but spans only two log sources;
\texttt{privilege\_escalation} carries 82 lines but spans five
distinct \texttt{(source\_host, source\_log)} pairs (audit on host,
auth, access, cpu, dnsmasq).

\textbf{Insight.} Spread and volume rank the phases differently. The
spread metric is what motivates the cross-source joins in queries A4
through A7 and the saved view: a phase that lives on five logs is one
the database can describe more completely than any single log can.

\subsubsection{A1 (Ishaan): Distinct event types on labeled hosts (EXISTS subquery)}
\textbf{Category.} Subquery (\texttt{EXISTS}). \\
\textbf{Question.} Which audit event types appear on hosts that have
at least one labeled log line, anywhere in the corpus?
\begin{lstlisting}[language=SQL]
SELECT DISTINCT e.type
FROM audit_event e
WHERE EXISTS (
  SELECT 1
  FROM host h
  JOIN labeled_line ll
    ON ll.source_host = h.host_key
  WHERE h.host_id = e.host_id
);
\end{lstlisting}

\textbf{Result.} 15 distinct audit-event type values: PAM, service
lifecycle, login, syscall, AVC, proctitle, user-cmd, user-login.

\textbf{Insight.} The \texttt{EXISTS} subquery is a simple existence
test, but it confirms that every audit-event type observed in the
corpus also coexists with at least one labeled line on the same host.
There is no audit-event type that is exclusively benign in the
recorded data, which justifies treating the audit subtypes as a
unified analysis surface in queries A4 onwards.

\subsubsection{A2 (River): Cross-source distribution of labeled lines (multi-CTE + CROSS JOIN)}
\textbf{Category.} Common table expression (two CTEs) + \texttt{CROSS
JOIN}. \\
\textbf{Question.} What share of labeled lines comes from each
\texttt{(source\_host, source\_log)} pair?

\begin{lstlisting}[language=SQL]
WITH per_source AS (
    SELECT source_host, source_log, COUNT(*) AS line_count
    FROM labeled_line
    GROUP BY source_host, source_log
),
total AS (
    SELECT SUM(line_count) AS total_count FROM per_source
)
SELECT ps.source_host,
       ps.source_log,
       ps.line_count,
       ROUND(100.0 * ps.line_count / t.total_count, 2)
         AS pct_of_all_labeled
FROM per_source ps
CROSS JOIN total t
ORDER BY ps.line_count DESC;
\end{lstlisting}

\textbf{Result.} Eight rows, one per labeled
\texttt{(source\_host, source\_log)} pair. The top row is
\texttt{internal\_share/dns.log} with 53\%+ of all labeled lines;
\texttt{intranet\_server/access.log.2} is next at roughly 12\%; and a
long tail covers the remaining six pairs at low single digits.

\textbf{Insight.} The \texttt{CROSS JOIN} against the single-row
\texttt{total} CTE is the standard SQL idiom for a percentage column
that does not require a window function. The result is the canonical
``fat head'' shape that explains why the abstract emphasises spread
over volume: most of the corpus is one phase on one log.

\subsubsection{A3 (Ishaan): Busiest day per host (window function)}
\textbf{Category.} Window function (\texttt{RANK() OVER PARTITION
BY}). \\
\textbf{Question.} On what day did each host generate the most audit
events?

\begin{lstlisting}[language=SQL]
SELECT h.host_key,
       DATE(e.timestamp) AS event_date,
       COUNT(*) AS events_that_day,
       RANK() OVER (
           PARTITION BY h.host_key
           ORDER BY COUNT(*) DESC
       ) AS day_rank_for_host
FROM audit_event e
JOIN host h ON h.host_id = e.host_id
GROUP BY h.host_key, DATE(e.timestamp)
ORDER BY h.host_key, day_rank_for_host, event_date;
\end{lstlisting}

\textbf{Result.} Eight rows: four event-days for
\texttt{intranet\_server} and four for \texttt{internal\_share},
ranked within each host. On \texttt{intranet\_server} the busiest day
is 2022-01-23; the attack day (2022-01-24) ranks third.

\textbf{Insight.} The attacker's audit activity is below the host's
baseline, not above it. This is the key fact behind the ``hides in
baseline'' framing in Section~\ref{sec:dashboard}: a detection rule
that triggers only on per-day audit-event-count outliers would miss
the attack on this host.

\subsubsection{A4 (Naman, Q1 of \texttt{naman\_advanced\_queries.sql}): Privilege-escalation reconstruction}
\textbf{Category.} CTE + \texttt{string\_agg} over a grouping +
multi-table join. The CTE body joins \textbf{seven} tables:
\texttt{audit\_event}, \texttt{host}, \texttt{labeled\_line},
\texttt{labeled\_line\_label}, \texttt{attack\_label},
\texttt{attack\_phase}, and a \texttt{LEFT JOIN} to
\texttt{audit\_message} (so the PAM message columns are nullable on
events that have no msg blob). \\
\textbf{Question.} Can we reconstruct the exact privilege-escalation
attack sequence on \texttt{intranet\_server}?

\begin{lstlisting}[language=SQL]
WITH attack_timeline AS (
    SELECT ae.event_id,
           ae.timestamp,
           ae.type AS audit_type,
           am.op   AS pam_operation,
           am.acct AS target_account,
           am.exe  AS executable,
           am.terminal,
           al.label_name,
           ap.phase_name
    FROM audit_event ae
    JOIN host h          ON h.host_id = ae.host_id
    JOIN labeled_line ll ON ll.source_host = h.host_key
                        AND ll.source_log  = 'audit.log'
                        AND ll.line_number = ae.line_number
    JOIN labeled_line_label lll
      ON lll.labeled_line_id = ll.labeled_line_id
    JOIN attack_label al ON al.label_id = lll.label_id
    JOIN attack_phase ap ON ap.phase_id = al.phase_id
    LEFT JOIN audit_message am ON am.event_id = ae.event_id
    WHERE h.host_key = 'intranet_server'
)
SELECT event_id, timestamp, audit_type, pam_operation,
       target_account, executable, terminal,
       string_agg(label_name, ', ' ORDER BY label_name) AS labels
FROM attack_timeline
GROUP BY event_id, timestamp, audit_type, pam_operation,
         target_account, executable, terminal
ORDER BY timestamp, event_id;
\end{lstlisting}

\textbf{Result.} Nine rows that decompose into two distinct attack
bursts:
\begin{itemize}
  \item Burst 1 at 2022-01-24 04:37:40 UTC: a \texttt{su} from
    \texttt{www-data} to \texttt{jhall} via \texttt{/bin/su} (four
    PAM events: USER\_AUTH, USER\_ACCT, CRED\_REFR, USER\_START).
  \item Burst 2 at 2022-01-24 04:38:06 UTC: \texttt{sudo cat
    /etc/shadow} via \texttt{/usr/bin/sudo} as \texttt{jhall} (five
    events: USER\_CMD plus four PAM events). Burst 2 begins 25.6
    seconds after burst 1.
\end{itemize}

\textbf{Insight.} The reconstruction is only possible because audit
events, host inventory, and attack labels live in the same database
with cross-domain provenance keys. Each of the seven joined tables
contributes an irreducible fact: \texttt{audit\_event} for the
timeline, \texttt{audit\_message} for the executable name and target
account, \texttt{host} for the human-readable host key,
\texttt{labeled\_line} for the audit-log line number,
\texttt{labeled\_line\_label} and \texttt{attack\_label} for the
ground-truth label, and \texttt{attack\_phase} for the kill-chain
phase. The query is the rubric's ``multi-table join (three or more
tables)'' line item with margin to spare.

\subsubsection{A5 (Naman, Q2 of \texttt{naman\_advanced\_queries.sql}): Detection-rule effectiveness across all phases}
\textbf{Category.} CTE + window function (\texttt{DENSE\_RANK}) +
three-table join. \\
\textbf{Question.} Across every kill-chain phase, which detection
rules are most effective at identifying labeled attacker activity?

\begin{lstlisting}[language=SQL]
WITH rule_stats AS (
    SELECT llr.rule_name,
           ap.phase_name,
           COUNT(DISTINCT llr.labeled_line_id)
             AS lines_triggered,
           COUNT(DISTINCT llr.label_id)
             AS labels_triggered
    FROM labeled_line_rule llr
    JOIN attack_label al ON al.label_id = llr.label_id
    JOIN attack_phase ap ON ap.phase_id = al.phase_id
    GROUP BY llr.rule_name, ap.phase_name
)
SELECT rule_name,
       phase_name,
       lines_triggered,
       labels_triggered,
       DENSE_RANK() OVER (ORDER BY lines_triggered DESC)
         AS effectiveness_rank
FROM rule_stats
ORDER BY lines_triggered DESC
LIMIT 15;
\end{lstlisting}

\textbf{Result.} 15 rows. \texttt{dnsteal.domain.match} is rank 1 with
roughly 53K lines triggered (exfiltration). Audit-derived rules
(\texttt{escalate.via.su}, \texttt{escalate.via.sudo}, etc.) sit
between rank 6 and rank 12 with low double-digit line counts.

\textbf{Insight.} Volume-based ranking is not a substitute for
kill-chain coverage. The audit-rule cluster has five orders of
magnitude fewer firings than the DNS-tunneling rule but is the only
rule class that catches the privilege-escalation phase. Query A14
re-ranks the same population after restricting to the
\texttt{privilege\_escalation} phase, which surfaces the audit rules
to the top of the table.

\subsubsection{A6 (Naman, Q3 of \texttt{naman\_advanced\_queries.sql}): Lateral-movement timeline}
\textbf{Category.} CTE + multi-table join (the same seven-table shape
as A4: \texttt{audit\_event}, \texttt{host}, \texttt{labeled\_line},
\texttt{labeled\_line\_label}, \texttt{attack\_label},
\texttt{attack\_phase}, plus \texttt{LEFT JOIN audit\_message}) +
\texttt{COALESCE}. \\
\textbf{Question.} Can we trace the attacker's movement across hosts
in a single ordering?

\begin{lstlisting}[language=SQL]
WITH labeled_audit AS (
    SELECT h.host_key,
           ae.timestamp,
           ae.type AS audit_type,
           am.acct AS target_account,
           am.exe  AS executable,
           am.unit AS service_unit,
           ap.phase_name,
           string_agg(al.label_name, ', '
                      ORDER BY al.label_name) AS labels
    FROM audit_event ae
    JOIN host h          ON h.host_id = ae.host_id
    JOIN labeled_line ll ON ll.source_host = h.host_key
                        AND ll.source_log  = 'audit.log'
                        AND ll.line_number = ae.line_number
    JOIN labeled_line_label lll
      ON lll.labeled_line_id = ll.labeled_line_id
    JOIN attack_label al ON al.label_id = lll.label_id
    JOIN attack_phase ap ON ap.phase_id = al.phase_id
    LEFT JOIN audit_message am ON am.event_id = ae.event_id
    GROUP BY h.host_key, ae.timestamp, ae.type,
             am.acct, am.exe, am.unit, ap.phase_name
)
SELECT host_key, timestamp, audit_type, phase_name, labels,
       COALESCE(target_account, service_unit, '(n/a)')
         AS target_detail,
       executable
FROM labeled_audit
ORDER BY timestamp, host_key;
\end{lstlisting}

\textbf{Result.} 11 rows across two hosts. At 04:37 to 04:38 UTC,
\texttt{intranet\_server} shows the privilege-escalation chain (the
nine rows from query A4). At 13:50 UTC,
\texttt{internal\_share} shows two exfiltration events (the
\texttt{put} service from query B6).

\textbf{Insight.} The two bursts are nine hours apart on two different
machines. A single-log analysis would never see them together. The
relational schema lets us order them in one timeline, which is the
view the report's conclusion characterises as ``cross-source joins are
diagnostic.''

\subsubsection{A7 (Naman, Q4 of \texttt{naman\_advanced\_queries.sql}): Burst detection from timing alone}
\textbf{Category.} CTE + window functions (\texttt{LAG} and
\texttt{ROW\_NUMBER}). \\
\textbf{Question.} Can we identify distinct attack bursts from purely
temporal patterns, without consulting any label?

\begin{lstlisting}[language=SQL]
WITH labeled_audit_events AS (
    SELECT ae.event_id, ae.timestamp, ae.type,
           ROW_NUMBER() OVER (
             ORDER BY ae.timestamp, ae.line_number
           ) AS seq,
           LAG(ae.timestamp) OVER (
             ORDER BY ae.timestamp, ae.line_number
           ) AS prev_timestamp
    FROM audit_event ae
    JOIN host h          ON h.host_id = ae.host_id
    JOIN labeled_line ll ON ll.source_host = h.host_key
                        AND ll.source_log  = 'audit.log'
                        AND ll.line_number = ae.line_number
    WHERE h.host_key = 'intranet_server'
)
SELECT seq, timestamp, type,
       EXTRACT(EPOCH FROM timestamp - prev_timestamp)
         AS seconds_since_prev,
       CASE
           WHEN prev_timestamp IS NULL THEN 'FIRST EVENT'
           WHEN EXTRACT(EPOCH FROM timestamp - prev_timestamp) > 10
                THEN 'NEW BURST'
           ELSE 'continuation'
       END AS burst_indicator
FROM labeled_audit_events
ORDER BY seq;
\end{lstlisting}

\textbf{Result.} Two distinct bursts separated by a 25.6-second gap.
Burst 1 (events 1 to 4): four \texttt{su} steps within 24
milliseconds of each other. Burst 2 (events 5 to 9): the sudo chain.

\textbf{Insight.} Without ever consulting the label tables, the
\texttt{LAG} window over event timestamps reproduces the same
two-burst structure that query A4 derives from the labels. This is a
useful unsupervised signal that complements rule-based detection: the
DBA can observe attack structure on a host even when no detection rule
has fired.

\subsubsection{A8 (Ishaan): Audit event types touched by the privilege-escalation chain (EXISTS, story-scoped)}
\textbf{Category.} Subquery (\texttt{EXISTS} with a four-table body)
+ \texttt{DISTINCT}. \\
\textbf{Question.} Which audit event types appear on the same
\texttt{intranet\_server} lines that carry a
\texttt{privilege\_escalation} label?

\begin{lstlisting}[language=SQL]
SELECT DISTINCT ae.type AS audit_type
FROM audit_event ae
JOIN host h ON h.host_id = ae.host_id
WHERE h.host_key = 'intranet_server'
  AND EXISTS (
      SELECT 1
      FROM labeled_line ll
      JOIN labeled_line_label lll
        ON lll.labeled_line_id = ll.labeled_line_id
      JOIN attack_label al
        ON al.label_id = lll.label_id
      JOIN attack_phase ap
        ON ap.phase_id = al.phase_id
      WHERE ll.source_host = h.host_key
        AND ll.source_log  = 'audit.log'
        AND ll.line_number = ae.line_number
        AND ap.phase_name  = 'privilege_escalation'
  )
ORDER BY audit_type;
\end{lstlisting}

\textbf{Result.} Eight distinct audit-event types fire on the
nine-event chain: \texttt{CRED\_ACQ}, \texttt{CRED\_DISP},
\texttt{CRED\_REFR}, \texttt{USER\_ACCT}, \texttt{USER\_AUTH},
\texttt{USER\_CMD}, \texttt{USER\_END}, \texttt{USER\_START}.

\textbf{Insight.} The chain triggers a specific subset of the
\texttt{auditd} taxonomy: every type fired is a credential or PAM
event (the \texttt{CRED\_*} family plus \texttt{USER\_AUTH},
\texttt{USER\_ACCT}, \texttt{USER\_START}, \texttt{USER\_END}) plus
the single \texttt{USER\_CMD} that records \texttt{sudo cat
/etc/shadow}. None of the noisy syscall, AVC, or proctitle types
appear, so a detector subscribed to just these eight types catches
the chain without needing the full \texttt{auditd} firehose.

\subsubsection{A9 (Ishaan): Busiest day on \texttt{intranet\_server} (RANK on a single host)}
\textbf{Category.} Window function (\texttt{RANK}) + \texttt{DATE}
truncation. \\
\textbf{Question.} On the host that carries the attack chain, which
day of the four-day window was busiest by raw audit volume, and where
does the attack day rank?

\begin{lstlisting}[language=SQL]
SELECT DATE(ae.timestamp) AS event_date,
       COUNT(*)           AS events_that_day,
       RANK() OVER (ORDER BY COUNT(*) DESC) AS day_rank
FROM audit_event ae
JOIN host h ON h.host_id = ae.host_id
WHERE h.host_key = 'intranet_server'
GROUP BY DATE(ae.timestamp)
ORDER BY day_rank, event_date;
\end{lstlisting}

\textbf{Result.} Four rows, one per day. The attack day
(2022-01-24) carries 565 audit events and ranks 3 of 4 days by raw
volume.

\textbf{Insight.} This is a cleaner version of A3 restricted to the
storied host. The chart on the dashboard (Section~\ref{sec:dashboard},
Panel 7) highlights the attack day in red so the audience can read the
``hides in baseline'' fact directly: the attack does not produce a
volume spike, so volume-only outlier detection would never flag the
day.

\subsubsection{A10 (Ishaan): Top detection rule per label inside the story phases}
\textbf{Category.} CTE + window function (\texttt{ROW\_NUMBER OVER
PARTITION}). \\
\textbf{Question.} For each label inside the \texttt{initial\_access}
and \texttt{privilege\_escalation} phases, which single rule fires the
most?

\begin{lstlisting}[language=SQL]
WITH rule_per_label AS (
    SELECT ap.phase_name,
           al.label_id,
           al.label_name,
           llr.rule_name,
           COUNT(*) AS times_triggered,
           ROW_NUMBER() OVER (
               PARTITION BY al.label_id
               ORDER BY COUNT(*) DESC, llr.rule_name
           ) AS rule_rank_in_label
    FROM labeled_line_rule llr
    JOIN attack_label al ON al.label_id = llr.label_id
    JOIN attack_phase ap ON ap.phase_id = al.phase_id
    WHERE ap.phase_name IN ('initial_access',
                            'privilege_escalation')
    GROUP BY ap.phase_name, al.label_id, al.label_name,
             llr.rule_name
)
SELECT phase_name,
       label_name,
       rule_name,
       times_triggered
FROM rule_per_label
WHERE rule_rank_in_label = 1
ORDER BY phase_name, times_triggered DESC, label_name;
\end{lstlisting}

\textbf{Result.} Roughly seven rows, one per (phase, label) inside the
two story phases, each row showing the single best-firing rule for
that label.

\textbf{Insight.} Inside \texttt{initial\_access} the
\texttt{foothold} label is dominated by a single high-volume rule (the
classic ``one rule to rule them all'' pattern). Inside
\texttt{privilege\_escalation} each label has a different
best-coverage rule, which means the privilege-escalation phase is
actually a cluster of micro-detectors rather than one big detector.

\subsubsection{A11 (River): Foothold-to-escalate journey (CTE + NTILE)}
\textbf{Category.} CTE + window function (\texttt{NTILE(3)}). \\
\textbf{Question.} How does the attacker's web-foothold-then-escalate
progression on \texttt{intranet\_server} look when the labeled
\texttt{access.log.2} lines are bucketed into thirds by line position,
and where in that journey do the privilege-escalation traces appear?

\begin{lstlisting}[language=SQL]
WITH access_labels AS (
    SELECT ll.line_number,
           al.label_name,
           ap.phase_name,
           NTILE(3) OVER (ORDER BY ll.line_number)
             AS journey_third
    FROM labeled_line ll
    JOIN labeled_line_label lll
      ON lll.labeled_line_id = ll.labeled_line_id
    JOIN attack_label al ON al.label_id = lll.label_id
    JOIN attack_phase ap ON ap.phase_id = al.phase_id
    WHERE ll.source_host = 'intranet_server'
      AND ll.source_log  = 'access.log.2'
      AND ap.phase_name IN ('initial_access',
                            'privilege_escalation')
)
SELECT journey_third,
       phase_name,
       label_name,
       COUNT(*)         AS labeled_lines,
       MIN(line_number) AS first_line,
       MAX(line_number) AS last_line
FROM access_labels
GROUP BY journey_third, phase_name, label_name
ORDER BY journey_third, phase_name, label_name;
\end{lstlisting}

\textbf{Result.} Roughly four to six rows, one per
(journey\_third, phase, label) inside the two story phases.
\texttt{initial\_access} foothold labels are spread evenly across the
three thirds; \texttt{privilege\_escalation} traces appear only in
the late third.

\textbf{Insight.} The attacker's web traffic establishes a foothold
across the entire \texttt{access.log.2} window before the
privilege-escalation phase ever fires. \texttt{NTILE(3)} is the
expressive choice here: a percentile bucket lets the chart audience
see the structural ordering without committing to a wall-clock axis.

\subsubsection{A12 (River): Foothold accumulation (CTE + cumulative SUM window)}
\textbf{Category.} CTE + aggregate-in-window
(\texttt{SUM(COUNT(*)) OVER (ORDER BY ...)}). \\
\textbf{Question.} How does foothold evidence accumulate as we walk
through \texttt{access.log.2} line by line, in 1{,}000-line buckets?

\begin{lstlisting}[language=SQL]
WITH foothold_lines AS (
    SELECT ll.line_number,
           (ll.line_number / 1000) * 1000 AS line_bucket
    FROM labeled_line ll
    JOIN labeled_line_label lll
      ON lll.labeled_line_id = ll.labeled_line_id
    JOIN attack_label al ON al.label_id = lll.label_id
    WHERE ll.source_host = 'intranet_server'
      AND ll.source_log  = 'access.log.2'
      AND al.label_name  = 'foothold'
)
SELECT line_bucket,
       COUNT(*) AS foothold_in_bucket,
       SUM(COUNT(*)) OVER (ORDER BY line_bucket)
         AS foothold_cumulative
FROM foothold_lines
GROUP BY line_bucket
ORDER BY line_bucket;
\end{lstlisting}

\textbf{Result.} Roughly eight rows, one per 1{,}000-line bucket of
\texttt{access.log.2}. The cumulative running total climbs to
approximately 7{,}691 by the final bucket.

\textbf{Insight.} The aggregate-in-window pattern
(\texttt{SUM(COUNT(*)) OVER (ORDER BY ...)}) is the SQL idiom for a
running-total chart. Plotted as a step curve in the dashboard
(Section~\ref{sec:dashboard}, Panel 2), the result shows where the
foothold density sits on the log so the audience can correlate it
with the privilege-escalation timestamp from query A4.

\subsubsection{A13 (River): Privilege-escalation source spread (CTE + RANK)}
\textbf{Category.} CTE + window function (\texttt{RANK}) +
\texttt{COUNT DISTINCT}. \\
\textbf{Question.} How does \texttt{privilege\_escalation} evidence
spread across the five different log sources that observed the same
attack?

\begin{lstlisting}[language=SQL]
WITH source_evidence AS (
    SELECT ll.source_host,
           ll.source_log,
           COUNT(DISTINCT lll.labeled_line_id)
             AS labeled_lines,
           COUNT(DISTINCT al.label_id)
             AS distinct_labels
    FROM labeled_line ll
    JOIN labeled_line_label lll
      ON lll.labeled_line_id = ll.labeled_line_id
    JOIN attack_label al ON al.label_id = lll.label_id
    JOIN attack_phase ap ON ap.phase_id = al.phase_id
    WHERE ap.phase_name = 'privilege_escalation'
    GROUP BY ll.source_host, ll.source_log
)
SELECT source_host,
       source_log,
       labeled_lines,
       distinct_labels,
       RANK() OVER (ORDER BY labeled_lines DESC) AS volume_rank
FROM source_evidence
ORDER BY volume_rank, source_host;
\end{lstlisting}

\textbf{Result.} Five rows: the audit chain on
\texttt{intranet\_server/audit.log} (9 lines), plus side-channel
evidence on \texttt{intranet\_server/auth.log} (8 lines),
\texttt{intranet\_server/access.log.2} (4 lines),
\texttt{monitoring/cpu.log} (49 lines, dominated by the
\texttt{wpcrack} rule), and \texttt{inet-firewall/dnsmasq.log} (12
lines, dominated by the \texttt{webshell} rule).

\textbf{Insight.} The same 82-line privilege-escalation phase is
visible from five vantage points. A single-log review would only see a
fraction of the picture; the database lets every team member working
on a different log file converge on the same incident with confidence.

\subsubsection{A14 (Naman): Detection-rule effectiveness inside privilege escalation}
\label{sec:adv-naman-priv-esc}
\textbf{Category.} CTE + window function (\texttt{DENSE\_RANK}) +
three-table join, story-scoped. \\
\textbf{Question.} Restricted to the \texttt{privilege\_escalation}
phase only, which detection rules catch the most labeled lines?

\begin{lstlisting}[language=SQL]
WITH rule_stats AS (
    SELECT llr.rule_name,
           COUNT(DISTINCT llr.labeled_line_id)
             AS lines_triggered,
           COUNT(DISTINCT llr.label_id)
             AS labels_triggered
    FROM labeled_line_rule llr
    JOIN attack_label al ON al.label_id = llr.label_id
    JOIN attack_phase ap ON ap.phase_id = al.phase_id
    WHERE ap.phase_name = 'privilege_escalation'
    GROUP BY llr.rule_name
)
SELECT rule_name,
       lines_triggered,
       labels_triggered,
       DENSE_RANK() OVER (ORDER BY lines_triggered DESC)
         AS effectiveness_rank
FROM rule_stats
ORDER BY effectiveness_rank, rule_name;
\end{lstlisting}

\textbf{Result.} Roughly 8 to 12 rows. Top rule is the
\texttt{wpcrack} rule on \texttt{cpu.log} with the largest line count;
the audit-derived rules follow at lower volumes; the lowest-rank rules
fire only on a handful of \texttt{access.log.2} lines.

\textbf{Insight.} This is the same query pattern as A5 but with a
\texttt{WHERE} clause that restricts the population to a single phase.
The rerank surfaces the audit-domain rules to the top of the table
where they belong; in A5 they were buried under the
DNS-tunneling rule. The pair (A5, A14) is the small data-engineering
lesson: ``rank within the population that matters, not across all
populations.''

\subsection{Performance: Indexing and EXPLAIN ANALYZE}
\label{sec:explain}
% =========================================================================

\subsubsection{Workload: Incident-Response Zoom}
The query that motivates the index is the classic incident-response
access pattern: an analyst already knows roughly when something went
wrong (e.g., from a SIEM alert) and zooms into a narrow time window on
a specific host. On the loaded database that translates to:

\begin{lstlisting}[language=SQL,basicstyle=\ttfamily\footnotesize]
SELECT ae.timestamp, ae.type,
       am.op   AS pam_operation,
       am.acct AS target_account,
       am.exe  AS executable,
       am.terminal
FROM audit_event ae
JOIN host h
  ON h.host_id = ae.host_id
LEFT JOIN audit_message am
  ON am.event_id = ae.event_id
WHERE h.host_key = 'intranet_server'
  AND ae.timestamp
        BETWEEN '2022-01-24 04:37:30+00'
            AND '2022-01-24 04:38:15+00'
ORDER BY ae.timestamp;
\end{lstlisting}

The query returns the same nine-row privilege-escalation chain that
query A4 produces from a different angle (no label join, just the
host plus timestamp predicate). The full file with both
\texttt{EXPLAIN ANALYZE} plans and the Alembic-only reproduction
recipe is
\texttt{naman\_explain\_index\_improvement.sql} under
\texttt{sql/queries/advanced/}.

\subsubsection{Index Definition}
The composite index lives in the canonical DDL file
\texttt{sql/3nf/\_indexes.sql} and is created by Alembic migration
\texttt{742e860d116f}:

\begin{lstlisting}[language=SQL]
CREATE INDEX IF NOT EXISTS
  idx_audit_event_host_timestamp
ON audit_event (host_id, timestamp);

ANALYZE audit_event;
\end{lstlisting}

The leading column is \texttt{host\_id} (the equality column in the
filter), followed by \texttt{timestamp} (the range column). This
ordering lets the planner satisfy both predicates with a single index
scan.

\subsubsection{Before/After Plan Summary}
Both plans were captured 2026-05-01 against the loaded
\texttt{russellmitchell} slice (3{,}048 \texttt{audit\_event} rows).
Table~\ref{tab:explain} reports the headline numbers; the full
\texttt{EXPLAIN (ANALYZE, BUFFERS)} text for both plans, plus the
Alembic-only reproduction recipe (downgrade, ANALYZE, EXPLAIN; then
upgrade, ANALYZE, EXPLAIN), is recorded in
\texttt{naman\_explain\_index\_improvement.sql} in the repository.

\begin{table}[htbp]
\caption{Compact \texttt{EXPLAIN ANALYZE} summary for the
incident-response zoom query, before and after the composite index
\texttt{idx\_audit\_event\_host\_timestamp}.}

\textbf{Metric} & \textbf{Before} & \textbf{After} \\

\subsubsection{Discussion}
Four improvements come out of the new index. (1) The plan node on
\texttt{audit\_event} flips from \texttt{Seq Scan} (3{,}039 rows
discarded by the timestamp filter) to \texttt{Index Scan} where the
single \texttt{Index Cond} covers both host equality and the
timestamp range. (2) Execution time drops from 1.462~ms to 0.640~ms
(about 2.3 times faster on the small slice). (3) Buffers shared hit
drops from 141 to 33 (about 4 times less I/O). (4) The planner cost
estimate drops from 171.22 to 24.79. The improvement scales with
\texttt{audit\_event} row count; the planner-statistic shift (cost
171 to 25) shows the same proportional win that would be felt on the
full corpus, where \texttt{audit\_event} would be roughly five times
larger.
